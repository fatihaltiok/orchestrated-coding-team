The short version
I don't write code, and honestly I can't really read it either. Still, I run about 25 projects at
the same time: tools for clients, tools for my own work, films, course material. The code
comes from AI agents. My part is to say what should exist, to approve anything that costs
money or goes public, and to set the rules.
What makes this work is a team with a lead, not one clever agent. One model, Claude, is
the orchestrator. It plans, writes down how the parts have to fit together, hands out the
work and checks every result. Several coding agents from different companies build the
parts, each one in its own copy of the project.
Everything rests on one idea: if it matters, it lives in a file and a tool checks it. Nobody
has to remember it. AI models forget. When their working memory fills up, they
summarize the conversation so far, and a 2026 study planted standing instructions such
as "do not delete any emails until I confirm" in test sessions and found that the
summarizers it tested kept only 17 % of them on average (Wang et al. 2026). So every
instruction I give, every decision and every task is a file, and wherever we can, a small
program checks the rule instead of hoping someone remembers it.

combination, run by someone who never looks at the code. That's what this report is
about. It ends with a blueprint (Appendix A) so others can set up something similar.

Where I'm coming from
Not being a developer gives me three problems a single agent can't solve:
I can't catch bugs myself. So I need checks I can trust more than my own eyes.
My instructions have to stick. Something like "ask me before you spend money" holds
for weeks, across dozens of sessions and restarts.
Big projects have to stay manageable. The bigger a project gets, the more a single
agent would have to keep in its head, and the more it forgets.
The answer looks a lot like a normal human team: a lead who plans and checks, specialists
who build, and written agreements that don't depend on anyone's memory. The one big
difference: everyone on this team except me forgets everything the moment their session
ends. So the whole setup has to expect forgetting from day one.

Stage 5 started with a message from me on 26 September. It said, roughly (translated from
German): this should work across all projects, "so we can work more efficiently, faster,
safer and smarter, no matter how complex the projects get." It was built in eight packages
(U0 to U7) over two days, by the team's own agents, under the same rules they were
putting in place.

The team
The agents come from different companies on purpose. Every model has blind spots, and
a mistake one of them misses, another one often catches. Not always, though. Strong
models from different vendors often make the same mistakes (Kim et al. 2025), and in one
study a review by another vendor's model lowered the share of passing solutions instead
of raising it (Xiang et al. 2026). That's why our reviewer never changes anything, and a
finding only counts once the orchestrator has reproduced it. The main staffing rule:
whoever reviews never comes from the same company as whoever built it.

The architecture
There are two sides. On the left is what lives on disk permanently and survives every

There's only one way back: if the review finds something, the task gets reworked and built
again.

All tools live in one shared repository and every project uses them through short
commands. There are deliberately no per-project copies, because copies drift apart. The
tools themselves are covered by 499 automated tests (counted on 27 September 2026).
(The tool names are German, because that's the language I work in.)

One real example, step by step
On 27 September 2026 we wanted the team's memory to go into every context package
(package U7). From my OK to "done" took less than an hour. Here's what happened:
1. I decide. I wanted the collected lessons in every task: "I need your notepad in the
folder, we don't always have client data" (translated). The orchestrator had advised
against it, because some notes contain client names. The decision went into the log
with both sides: what was chosen, what was rejected, and why.
2. A plan in plain language. The orchestrator told me who builds (Devin), who reviews
(Muse), and what it costs (review about 1–2 dollars, Jev under 2 cents per package).
My answer: "yes, start".
3. Contract first. The orchestrator wrote the contract section itself: what behavior is
required, how to switch it off, and which eleven test cases have to prove it.
4. Task and context package. Both were written as files and committed before the agent
started. What isn't committed doesn't make it into the working copy.
5. Start in its own copy. The run watcher started Devin. Its first move was to check the
context package: is it complete and current? An out-of-date package stops the run.
That actually happened earlier the same day on another package, and stopping was the
right call.
6. Look, then merge. Once the done file was there, the tool saved the state, the
orchestrator read the diff against the contract, and the tests ran in the copy. Only then
was it merged.

7. Review by another company. Muse read the code without changing anything and
found two real gaps. A dead link in the notes folder made every package build fail, and a
link pointing outside the folder got read too, so outside files could have ended up in the
package and been sent on to Jev.
8. Reproduce, then fix the contract. The orchestrator reproduced both findings itself
before treating them as real, and added to the contract. The hole was in the contract;
the builder had just followed it.
9. Fix. Devin fixed it in a fresh working copy. Afterwards Muse's own evidence scripts no
longer found anything, and all 499 tests passed (27 September 2026).
10. Real trial. A context package for a real task showed the right notes, Jev cost about half
a cent, and the memory stayed untouched.
11. Wrap-up. Final check, status updated, restart check by two fresh agents. It was only
pushed after my explicit OK ("yes do it").
On bigger projects, several tasks like this run at the same time, each in its own copy.
They're merged one after another, and each merge first pulls in the newest main project
and tests how everything works together. The part that connects everything comes last,
on its own. For critical pieces there's the double build: two agents from different
companies build the same task independently, the orchestrator keeps the better result
and throws the other away.

Protecting context
What "context" means
Every AI model has a limited working memory, its context. Everything it reads, writes or
gets back in a session takes up space. When it's full, the conversation so far gets
summarized. What gets lost is whatever seems unimportant to the summary: details,
reasons, and above all instructions like "ask me first". The study "Lost in Compaction"
(2026) measured that such instructions survive summarizing only 17 % of the time on
average. The rate varied with the summarizing model, its prompt and the wording of the
instruction, but no setting fixed the loss. The authors show a way out: a small extra model
runs alongside, collects the instructions in its own list and adds them back after
summarizing, which keeps over 90 %. We follow the same idea with different means: the
instructions sit word for word in files, and tools check that they reach the agent. We
haven't tested our approach on their benchmark.

Why a team helps
The orchestrator doesn't read piles of files. The agents read the code; what comes
back is a report and a diff. Its context stays free for architecture, review and the big
picture.
Each agent only needs its own area. With its own copy, a clear task and a context
package, an agent doesn't have to understand the whole project. Models with smaller
memory only get small, tightly scoped tasks.
Waiting costs nothing. The run watcher waits up to nine minutes at a time and then
reports back, instead of the orchestrator asking every few seconds.

The context package
"Read all the project's rules and decisions before you start" sounds simple. But on 26
September, in our biggest project, those lists were about 305,000 bytes long, roughly
76,000 tokens. No agent reads that reliably from start to finish, and nobody can see what
it skipped. That's exactly how an agent had ignored a build rule two weeks earlier.
The context package fixes this by splitting things in two:
The must-read part, complete and word for word: every instruction I've given that still
applies, every valid decision at least with its core sentence and where to find it, the
decisions relevant to this task in full, and the current status. No model is allowed to
remove anything from this part.
The extra part, only sorted: lessons from the memory and related sections. Jev
suggests the reading order. Nothing gets dropped.
Every package comes with a checksum file listing all sources. The tool kontextpaket
pruefe uses it to notice when an instruction is missing, a source has changed since the

package was built, or the status is stale. If a package gets too big, it's split into parts,
never cut off. We rejected two tempting shortcuts: having a model summarize the lists (it
would reword my instructions, which is the very thing we're trying to prevent) and "only
the newest entries" (old decisions that still apply would silently drop out).

One rule file for every agent
The working rules sit in a file every model loads at the start of each session and again after
every summary. But Claude and Codex read different files, and we used to maintain them
by hand. A comparison on 26 September found that the Codex copy was missing 31 of 137
rules, and 7 more said something different. It also mentioned a tool that had been gone
for days.

Since 27 September there's one source, and both files are generated from it. When we
switched, the generated Claude file had to match the old one byte for byte, so we knew
for sure no rule got lost. Since then, the final check reports any installed file that drifts
from its source. A quick test showed the difference: afterwards Codex named the right
second-opinion model, the right command for fix-up rounds, and the tool rules it had been
missing.
We did the same with the project index every session loads. It had grown to 76,983 bytes,
because each new status got written above the old one. Codex only read the first 32,768
bytes of it, so 43 %. Now it's 16,542 bytes: per project just the entry file and one status
line that replaces the old one. The history lives in the projects. A small script keeps size
and format in check.

The restart check: before every restart and after every finished package, two fresh
agents with no background knowledge go through the handover notes. One only reads
and lists every spot where it would have to guess. The other actually runs the
commands and reports what doesn't match. Both read the original files, never just the
context package. Otherwise one mistake in the selection would hide the same gap
from both, and them agreeing would just be an echo.

The memory
The team's memory is a folder with a short index and 209 single notes (counted on 5
October 2026). Most of them are lessons from mistakes: which model gets what wrong,
which check doesn't actually measure anything, which command has a trap in it. The
index-plus-notes setup comes with Claude Code: the index is loaded in every session
without asking, and notes are read when needed. What we added is a form check, a
lossless restructuring instead of trimming, and putting the memory into the context
package. It's the only layer that works across projects. Something learned on a film project
is there when a client project needs it.

A wrong note gets believed
Until 21 September 2026, this biggest store of knowledge had not a single written rule,
and nothing checked it. That's worse than a missing test in code: a broken test turns red, a
wrong note gets believed. The first run of our new checker, merkzettel-check , found ten
places where notes pointed to files that no longer existed, plus five links between notes
that led nowhere. One of those notes described a film that had been lost in a data loss on
20 September as if it were still there.
Since then, the shape of the memory is rank 1. Nothing is orphaned, no link points
nowhere, the index stays under its loading limit, and a path written in code format is a
promise that it exists. When something's gone, the note keeps it, but without the code
format and with a date. The content stays manual work. No tool can tell if a note is still
true, and the contract says so on purpose, so a green run doesn't get mistaken for a
healthy memory.

No vector database
The obvious move would have been a vector database that finds notes by meaning
instead of words. Our own test on the real notes said otherwise. For three search
questions, plain grep found the right note in the top four twice, the best meaning-based
model only once. The study "Is Grep All You Need?" (2026) reaches a similar result in

The Orchestrated Coding Team

some of its comparisons. It looked at conversation memory, not code, though, and
stresses that the result depends a lot on the agent tool. Three questions are a hint, not
proof, and we can change our minds.
The deeper reason is something else. A database improves how well things are found, not
whether anyone looks. A model doesn't look something up if it has no idea there's
something to know. What helps is a short index that's loaded without asking, not a better
search engine.

Keeping details instead of trimming
When the index hit its loading limit, the easy fix would have been to merge similar notes. I
said no: "no, that's not good, if you have to leave out details, we'll do it differently"
(translated). Keeping details is the whole point of the memory; cutting it down to fit a limit
turns that upside down. We solved it without losing anything: several links per index line,
and project statuses that had crept into the index moved into the notes, after a script had
checked that every sentence had made it over. 165 index lines became 45, and no note
was shortened.

Jev, a judging model
Jev (made by TypeSafe) isn't a language model that writes text or code. It answers narrow
questions with a number or a choice, fast and for a fraction of a cent. On our team it has a
tightly limited role, written into the contract:
Jev sorts and never filters. It suggests in what order extra material should be read. It
never takes anything out of the must-read part of a context package.
Jev approves nothing. No judgment from Jev replaces a test, a review or a decision by
me.
If Jev fails, you see it. Then plain keyword order applies, and the package says "not
rated".
Every request has a control: a text with nothing to do with the task goes along and has
to get a low score. If it doesn't, the model isn't judging, it's just nodding.
Nothing secret goes out. Before sending, a tool looks for patterns of passwords and
access keys and holds those sections back. The model version is fixed, so a silent
model update can't spoil the measurement.

First use: ask about the action, not a number
On 21 September we wanted to know if the memory had duplicate notes. A similarity
score didn't help: the values for all pairs were spread out evenly, with no clear gap
between "similar" and "different". Any cut-off would have been arbitrary. Jev's own

Page 14 of 34

The Orchestrated Coding Team

documentation suggests something else: ask directly about the action, with three levels
matching the three things you can do: keep them apart, show them to a human, merge
them. Then there's no threshold to tune to your data.
The full run over all 3,541 note pairs took 40 seconds. Result: not a single duplicate, but 137
related pairs that didn't link to each other yet. The judgment was 98 % repeatable. The
one pair that looked like a duplicate the first time flipped on the second run, because it
sat exactly on the border between two levels. Near a border, you read it yourself, you
don't round. And the strongest matches had almost no words in common. A keyword prefilter would have missed all of them.

setup was fixed and committed beforehand: five real tasks, a reference judgment from

of the time, and the orchestrator decided the ten disputed cases), a decision rule with
five conditions, and a spending cap of 10 cents. The reference was in the repository

Data protection
Jev runs on the vendor's servers, so task texts and notes leave our hands. Reading the
privacy policy word for word: TypeSafe promises in writing not to train on the data, but
keeps it with no fixed deletion date in the US. Zero retention is only for big customers. So
we switched Jev off for the one project with confidential company data. For the others I
accepted the transfer on purpose. The decision is in the log with both sides, and it can be
reversed per project with one line.

Quality checks
An agent saying "done" has only made a claim. Code is done when it passes objective
checks, the orchestrator has read it, and an outside reviewer finds nothing more. The
chain:
1. Spec before building. The contract says what has to be tested before any agent writes
code.
2. Gates with a counter-test. Automated tests, and stricter methods for critical code.
Every test has to fail when you put the bug back in on purpose. Otherwise it's not
testing anything.
3. Review by the orchestrator. It reads the code against the contract, not just the test
results.
4. Review by another company. Read-only, with evidence for every finding. The
orchestrator reproduces each finding before it counts, which also weeds out the
reviewers' false alarms.
5. A real-world run. The result gets used once on real material, not just tested.

The team channel
Since 1 October 2026, two lead sessions, Claude and Codex, can work together as equal
colleagues. Before that I was the messenger: I copied text from one window into the other.
The team channel is a small mailbox on my own computer. Every session gets its own ID
when it starts. A message to Claude shows up there as a new turn, even if nobody is
typing. A message to Codex goes into the running session through Codex's own
command. Stored, delivered and read are three different states: a message only counts as
read once the receiver confirms it.

What we've seen in real use
30 Sept: In the first live test, messages went both ways, for $0.04; only the last read
confirmation was missing. Then the test got stuck because Codex hit its usage limit.
Codex's small quota has been the bottleneck ever since.
1 Oct, early: A message from Codex woke up an idle Claude window without me typing
anything. The first try wasn't clear, because a command arrived in the window at the
same moment. The second one was.
1 Oct, afternoon: A small test run, a command that only waits 5 seconds, reported
"done" by itself right after it ended, in the Claude session that had started it.

them the same day. The script and its results are in the team's repository.

The human's role
The human on the team doesn't have to read code, but stays in control. That works
because the process only puts in front of me what I can actually judge, and leaves the rest
to reviewers who do read code.
I decide the what, not the how. Instead of "framework A or B?" the orchestrator asks
"should it run in the browser? should data be kept permanently?". It does the technical
translation itself and explains its recommendation in one sentence.
No agent starts without a plan and my OK. The plan comes in plain language: who
builds, who reviews, what it costs, what's different afterwards.
An OK is good for one thing only. Anything that costs money, goes public (uploading,
emails, publishing) or changes the shared rules needs an explicit OK, every single time.
An OK to build a tool isn't an OK to install it. Every approval goes into the log word for
word, with the date.
I always know where things stand. Before and after every bigger step, the orchestrator
tells me without being asked who's doing what, what's done, what's in progress and
what's still open.
The orchestrator names the risks, I decide. A few times I was right where it had advised
caution:
"The full run with Jev is cheap anyway": the orchestrator only wanted to check the 200
most promising note pairs. The full run found the strongest connections exactly where
the pre-filter wouldn't have looked.
"No, that's not good, if you have to leave out details": instead of merging notes, we built
a solution that loses nothing.
"I need your notepad in the folder": the orchestrator had advised against it because of

the per-project off switch keep the limits.
The other way round, the orchestrator never quietly takes a different path from what was
decided. Anyone who wants to change a valid decision first has to name the existing entry

Limits
This is experience, not a study. The measurements are small (three search questions,
five tasks), and there's no comparison group that worked without this setup. The
numbers show where the process caught bugs, not how many it prevents overall.
Tried by one person, not a team of people. Whether it holds up when several people
give approvals is an open question.
More admin. Every run has a branch, a copy, a context package, a result, a merge and
often a review. That's on purpose, because it swaps trust for proof, but it takes time.
Depending on vendors. In two weeks two models dropped out. The "other company
reviews" rule always needs at least two available vendors, and several vendors means
several bills.
The orchestrator makes mistakes too. Once it forgot the context package, once it built
a package before it had finished editing the docs. Both times a check caught it, and
since then the run watcher warns when a package is missing. Only what's checked by a
program can be relied on, and that goes for the orchestrator as well.
The memory's content can't be checked. No tool can say if a note is still true.
Data leaves our hands. The coding agents and Jev run at vendors, some in the US. For
client data and confidential company data that has to be decided per project.
Git only. The working copies need version control. Media projects without Git, and
runs that only read or report, go without them.

Page 26 of 34

The Orchestrated Coding Team

Badly split areas lead to conflicts. The working copy prevents damage, but not two
agents changing the same spot. Then nothing gets merged and the orchestrator has to
redo it. Good planning is still half the battle.
False "stuck" alarms. If an agent works outside its folder for a while or writes one huge
file in one go, the run watcher wrongly reports it as stuck. Then someone looks at the
session log.
There's evidence against parts of this. Working copies alone just push conflicts to
merge time (Liu et al. 2026). Changes from different agents clash twice as often as
changes from the same agent, 41.7 % vs 19.8 % (Xu et al. 2026). Context files like
AGENTS.md don't generally raise success rates and cost over 20 % more (Gloaguen et
al. 2026). Strong models from different vendors often make the same mistakes (Kim et
al. 2025), and a review by another vendor's model can even lower the pass rate,
depending on who reviews whom (Xiang et al. 2026). Our precautions (split areas,
contracts, merging one at a time, read-only reviewers) respond to that, but we haven't
measured whether they help.
The team channel is new. It has been running since 1 October 2026. Delivery and
waking up are proven. Handover and question list have only been tested. Whether two
lead sessions work better together than one hasn't been measured.
Bias. Large parts of this report were drafted with the orchestrator (Claude, by
Anthropic), which means a participant is describing its own way of working. I am the
sole author and responsible for all of its content.

What's next
A big program doesn't come out of one long agent run for us. It comes out of a series of
small, finished packages, each one small enough to plan, build, test and check on its own:
1. Skeleton and contracts first. Modules, data flows and interfaces are fixed before any
agent writes code.
2. Areas in parallel. Independent parts run at the same time in their own copies, each
with the agent that suits it.
3. Critical stuff twice. Core rules, money, data, security: two agents from different
companies, the orchestrator picks.
4. Merge early and often. Every merge tests how things work with everything that's
already there. So there's no big risky assembly at the end.
5. Every phase ends with something that runs, and it gets checked before the next one
starts.
6. Every important rule becomes a check. If it can be checked by a program, it becomes
a test or a lock instead of a sentence in the docs.

The format follows Architecture Decision Records (Nygard 2011). What we added:
"checkable by" is required, and the whole log goes into every agent's task. The last field
matters most. If you ask for every decision whether it can be turned into a check, you
slowly move it from "has to be remembered" to "gets checked every time".

Ten rules to take away
1. If it matters, it lives on disk, not in a model's head.
2. Instructions are kept word for word, never summarized.
3. Decisions get written down with what was rejected and why, right away, not at the end.
4. Contract first, then code.
5. Every agent that writes code works in its own copy.
6. "Done" is a claim; checks decide if it's true, not the report.
7. Nobody reviews their own work; review comes from another company.
8. Every check gets run once on real material.
